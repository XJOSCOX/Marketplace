# Image storage

Migration `202610020006_storage.sql` configures two **private** Supabase buckets:

| Bucket             | Paths                                                                 | Application writers                            | Readers                                                                             |
| ------------------ | --------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| marketplace-assets | `marketplaces/{marketplaceId}/logo/{randomUUID}.webp`                 | Marketplace owner/platform admin               | Managers, or anyone when the image is attached to an active marketplace             |
| product-images     | `marketplaces/{marketplaceId}/products/{productId}/{randomUUID}.webp` | Authorized product seller or tenant management | Authorized product managers, or anyone when attached to a publicly eligible product |

Objects cannot be overwritten through client UPDATE. Current authorized writers may DELETE. New names are generated by the server. Tenant/product ownership is resolved from database rows, not supplied user IDs, file names or metadata. Restrictive policies prevent unrelated permissive storage policies from widening these buckets' access. Bucket configuration and privileged operators remain trusted infrastructure.

The upload endpoint accepts raw PNG/JPEG/WebP bytes, up to 5 MiB and 16 megapixels. It checks magic signatures, decodes using Sharp, applies orientation, strips metadata and re-encodes as WebP at maximum 2400px. SVG/GIF/unsupported or malformed content is rejected; file extensions are irrelevant. Storage accepts WebP only and applies a 5 MiB bucket limit. The request uses the caller-scoped Supabase client, never a service-role credential. Logo upload requires owner permission; product upload resolves the product's seller and applies requireSellerAccess. Database CHECKs prevent attachment of another tenant/product path.

`POST /api/v1/marketplaces/:uuid/assets` uploads a logo. Add `?productId=:uuid` for a product primary image. Cookie requests need the exact APP_ORIGIN; mobile clients use a verified bearer token. Product rows must exist first. Upload and row attachment are not one cross-service transaction: if attaching fails, the service attempts to remove the newly uploaded object. Replaced images are retained privately for future cleanup; they are no longer anonymously readable after the pointer changes.

`GET` at the same URL resolves the saved image pointer under caller RLS, downloads from the private bucket and decodes/re-encodes again, returning `image/webp`, `nosniff`, `private, no-store`. The storefront uses this URL with image optimization disabled so draft preview cookies reach the authorized endpoint. No permanent public bucket URLs or long-lived signed URLs are issued. Publishing/unpublishing therefore changes future public access immediately (it cannot revoke files already downloaded by visitors).

Direct authenticated Supabase Storage calls still require the same path/RLS permissions and bucket limits, but Storage does not inspect magic bytes on behalf of this app. Such writes cannot bypass the image response decoder. Clients should use the versioned API, not raw Storage URLs. Do not enable public buckets or add broad unrestricted policies. Apply upload/decoder request quotas and orphan cleanup before production, as outlined in SECURITY.md.

No extra application secrets are needed. The Supabase Storage service and standard `storage.buckets` / `storage.objects` schema must exist before migration 006. Migrations create bucket records/policies; they do not provision a hosted project. Verify uploads/downloads using two actual users in a disposable project before deployment.

Future gallery support should use a tenant/product-scoped asset table with order and alt text, keep immutable unique object names, validate every upload through the same service, and add authorized removal/retention processing. Hero image uploads, gallery rearranging/cropping and automatic orphan cleanup are deferred; this phase implements logos and primary product images.
